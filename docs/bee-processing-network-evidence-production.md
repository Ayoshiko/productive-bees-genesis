### 10.22 D13a 共享计算内核与独立机接回（2026-09-19）

P2 未提交工作经审查、实际重跑全量测试和构建／产物检查后，以 `f960f32` 提交并推送。D13a 将无世界副作用的计算移到 `apiculture.production`：`BeeWorkConditions` 只接收工作基因和环境值，`BeeProgressPlan` 只规划已分配的虚拟 tick，`BeeProductionSampling` 只对一个有界轮数段计算数量。NBT 解析、真实物理槽修改、喂食、转化与物流仍由独立蜂箱适配器负责；能力预览与实际推进共用周期公式，不从已加速周期再次乘速度。

进度计划保留 long 完成周期与 STACK 周期数，先检查能耗乘法再允许物理状态改变；未获分配 tick 时，不因升级缩短周期而免费结算旧进度。正常调用方沿用已有按可支付 FE 分配 tick 的流程。物理 pending 的 int 饱和和旧升级轮数限制留在旧适配器中，不能将它们当作网络数量上限；D13b 必须持久化未处理轮数，按工作预算消费。结果入口返回模板与 long 数量，物理适配器才投影为 ItemStack；私有结果可直接使用现有 `ProductAmount`／分页表逐键相加，不能先截成 ItemStack 再反推精确余额。该入口的回调只是本次私有结果构建，不代表入库、付款或转移回执。

采样依赖由固定的 ThreadLocalRandom 类型改为调用方提供的 `RandomGenerator`，独立机仍传原线程随机源，算法和随机调用顺序保持原路径。确定性固定数量不消耗随机；二项轮数小批精确、大批沿用 Poisson／正态近似；普通基因的非定长数量和仍沿用原 `SampleUniformSum`，不能笼统声称所有小批逐次精确。非普通基因 ≤32 个成功样本逐栈取整，较大批次保持原分布近似；没有添加期望保底。未来网络的规划／SIMULATE 不可调用执行采样器，已付费结果冻结后不得再次抽样。

本地进一步核对 PB 13.13.5 的 `beeReleasePostAction`（基因逐栈取整、HasConverted 抑制蜜脾）及 `simulateBee`（会采收、收集、postPollinate 和调用产出），因此不把 PB 模拟入口作为纯函数复用。KubaTech `onStorageContentChanged` 的花源要求去重和加载期跳过世界检查可作缓存职责参考，不复制其 Forestry API。Useless `claimOutputs` 的按键整批所有权交付、ECO `InfiniteStorageAmounts` 的精确值与 long 投影分离用于明确数量边界；本轮没有复制参考实现或新增依赖。

验证记录：`build/p3-d13a-build.log` 的全量测试／构建／产物核验与探针编译通过；D13 阶段最终复核见 [10.23](#s10-23)。`build/network-probe-p3-d13a-noae2-1/results/domain.json` 在无 AE2 的 NeoForge 21.1.214 专服执行真实基础蜂箱生产处理器：两个铁蜂位分别为普通／极高生产力，10 个分配 tick 生成 2＋8＝10 个蜜脾，扣除 200 FE，喂食样本保持 1，余数与 pending 均为 0。另用合成极端数量配方证明三次数量回调可精确汇总 `13835058042397261827`，完整组件和原模板不变，物理投影仍为 int 上限。原 P2 托管隔离、往返、拓扑、8 类故障和正常停服也通过。该夹具在一个服务器 tick 内直接推进生产处理器，用于行为核对，不是 10 个真实服务器 tick 的性能测量；旧报告的 `realProductionExecuted=false` 属于 P1 夹具，D13a 的物理产出另列 `beeKernelPhysical*` 字段。

**D13a 交付时只完成共享计算和独立机接回。** 当时没有新增网络可执行蜜蜂记录、喂食账户或能量账户，也未改变 checkpoint schema。后续 D13b 见下节；未新增客户端界面，不将 P2 的截图作为生产验证。

### 10.23 D13b 逐蜂所有权、静态生产与恢复（2026-09-20）

`BeeRecord` 保留稳定 beeId、member／slot、完整原始数据、逐蜂生产力与工作基因、计划版本、付费余数、long 未采样轮数和 `ProductAmount` 冻结数量。`BeeMemberState` 只覆盖基础蜂箱的三个物理蜂位及有限 FE 保管账户；三个蜂位是本适配器已验证的物理布局，不是产物库存配额。工厂布局留给 D24，D16 再把有限 FE 从保管账户事务化移入全网账户，不能同时保留两份可用能量。

`StaticApiaryAdapter` 只读取封存映像和成员原位置，`NetworkBeeService` 验证当前核心、拓扑、目录 claim、成员绑定与空物理源后调用共享进度内核。付款与首段冻结结果先形成私有候选，再一次发布 checkpoint；预算为零时只保留已付费轮数，存在积压时不再接受新 tick。模拟不发布状态，也不调用随机源。无升级铁蜂为确定性路径，未将它包装成通用随机生产适配；D13a 原有概率模式边界仍成立。

结算复用 D06 的 PAID 事务语义，在私有账本候选中按精确键交付，再与清空蜂结果一起发布。已付费积压按保存计划恢复，不重新扣 FE、不依赖当前花源或重新选择配方；新工作重新检查条件、配方及能力版本。重复请求必须携带当前蜂 revision，旧 revision 不再入账。账本／策略版本不得回退，同一账本版本不得携带不同内容，防止旧运行来源覆盖刚结算的余额。现有保存测试的公共夹具也同步推进账本版本，因为它每次都会生成新的事务身份。

本地 PB JAR 的 `recipe/block_conversion/anvil_repair.json` 与 `anvil_repair_chipper.json` 证实铁蜂转化并非空集。第一次专服运行因此被保守准入拒绝；修正为显式要求关闭转化，并在探针中验证转化开启、Wanna 蜂和基因采样升级均被拒绝。使用铁块作为非消耗性样本时，普通／极高生产力两只蜂分别生成 2／8 蜜脾，总计 10，消耗 200 FE，与 D13a 独立机夹具一致。核心重建前已冻结一轮、保留一轮积压，恢复后结算一次，物理槽和储能始终为空；交还恢复两只原蜂、一个花样本和当前剩余 FE。

checkpoint schema 从 2 升至 3，生产状态随每成员所有权记录编码，并进入现有流式读取／预算恢复。错误类型、缺失生产状态、重复蜂位、未来配方版本和未知产物键导致整个域隔离；不会把错误当作空蜂箱。旧 schema 2 开发存档保持原文件并进入恢复状态，本步没有自动迁移旧测试世界。每成员最多三个记录的解码有明确范围，后续工厂扩展不能直接放宽为无界 RAW 列表。

### 10.24 D14 逐蜂位喂食与有限实物迁移（2026-09-20）

先复核工作区 D13 的独立机、所有权与 checkpoint 差异，重新执行构建／产物核验，通过后提交并推送 `583eceebce04a7e7127b02e9593026c63bc621d8`。随后按本轮要求对五个独立 Git 参考仓库执行 `pull --ff-only`，结果见 [13.2](bee-processing-network-references.md#s13-2)。PB／Mekanism 的固定版本源码没有 Git 元数据，继续用于核实本项目编译依赖的精确行为；未替换运行 JAR，也未将旧 KubaTech 摘录冒充最新源码。

新增 `apiculture.feeding` 的不可变物品身份、有限槽、共享组和工作计划；`StaticFeedingAdapter` 将版本相关物品 codec 与花源读取隔离，`NetworkFeedingService` 只在当前加载、有效归属的服务器边界提交。初次激活把蜂记录和喂食迁移候选一起发布；失败不留下半份可执行域。喂食从原映像移出后写 `feedingAuthority` 标记，保存和恢复同时要求账户与标记一致。交还按当前数量重建原 9 格物理布局，余格为空，不读取迁移前旧数量。

普通编辑与补料采用独立喂食 revision 和原不可变根校验，模拟不修改库存；补料仅移动实际可容纳量，剩余量留在来源槽。禁用槽不参加匹配／消耗，槽清空后解除禁用。共享消费的全部请求先在同一私有候选中扣除；缺料返回无计划，重复或过期计划不可提交。当前补料是成员有限槽之间的移动，外部供给入口属于 D16／D23；消费预约已做领域验证，实际转化／消耗性蜂种仍受 D25 准入限制，不能把纯计划接口称为已实现这些蜂种。

beeId 与当前位置解耦，移动蜂位保留完整 NBT、基因与已付费余数；原始槽数据只作交还模板，写回时采用当前 slotIndex。默认移动不带食物，显式带食物移动同时提交；共享状态不满足移动条件、目标占用或仍有待结算工作时拒绝。所有当前实现仅覆盖已验收的基础 3 蜂位，工厂和跨成员迁移按后续能力矩阵扩展。

checkpoint schema 升至 4，增加喂食账户。普通解码与预算解码均检查物品注册／组件完整往返、有限上限、数量、分组根及所属映像；不使用 Mekanism 的宽容解析把坏物品变成空栈。缺失账户和旧映像、重复保管或未知内容使整个域隔离。旧 schema 3 测试存档保持原文件并进入恢复状态，本步未自动迁移历史测试世界。物品只在有限喂食域保管，不会因此取得无限产物准入资格。

### 10.25 D15a 共享离心计算内核与物理路径回接（2026-09-20）

D14 已自审并以 `f624e86ddde7bed3413305e94b96160b86d4a1cb` 提交推送，开始本步时工作区干净且与远端一致。进入 D15 前再次对五个独立 Git 参考仓库执行 `pull --ff-only`；DataEnergistics 更新至 `47a416e0`，其余四个 HEAD 不变，详情见 [13.2](bee-processing-network-references.md#s13-2)。固定 PB／Mekanism 源码继续与本项目运行 JAR 对齐。

将 `PbVirtualTickPlan` 移入 `apiculture.centrifuge`，公开纯参数入口；`CentrifugeEnergyPricing` 承担每进程计费和可负担并行量，原 `MekCentrifugeEnergyScaling` 保留物理容量／升级／AE2 供能职责并委托该算法。物理 PB 和万象处理器调用同一个计划。未改变现有分段推进、少量输入、缺电、零 tick 折算和高并行计费算法，也未给能力池提供合并进程后的额外能耗折扣。

`CentrifugeProductionSampling` 只计算有界段的基础产量，`PbRecipeOutputSampler.QuantityOutput` 传递只读物品／流体模板、基础数量和倍率；`PbRecipeCompleter` 的单次和批量路径均已回接。基础量最大为 `Integer.MAX_VALUE²`，可精确保存在 long；网络接收方再用 `ProductAmount.multiply` 应用倍率，物理接收方继续按既有 int／long 边界饱和投影。没有把巨大数量展开成物品栈列表。回调只写本次私有结果；失败必须丢弃整个未提交结果，不能直接在回调内执行库存、AE2 或世界 IO。

本步固定以下语义，作为 D15b 的实施约束：

- **输入与倍率分离。** PB 原版 `CentrifugeBlockEntity` 把生产力数量同时用于扣输入；本项目既有行为是每完成一次操作扣 1 个输入，生产力仅放大物品和流体输出。本步保留后者，不能因为参考原版而改变已经采用的平衡。
- **批量概率属于兼容模式。** 单次保留概率检查的 nextFloat 与数量 nextLong 顺序，必定输出不消耗概率随机数。多次采用 `floor(Np)` 保底加剩余抽样、数量和沿用 CLT；它不是原始逐次二项分布，整数 Np 会得到确定的成功次数。网络必须记录有界采样段和冻结结果，不得把不同批量切分称为同一随机分布，更不能在重试时重抽已付费产物。
- **每进程独立计费。** 16 并行以内线性，之后每翻倍增加 1 个计费操作；例如两个 17 并行进程每 tick 共计 34 份单价，不能合并成 34 并行后只付 18 份。Mekanism `CachedRecipe.process` 的进度／输入／输出职责可参考，不能让网络运行隐藏方块实体 ticker 来借用其副作用。
- **进度值不足以恢复网络作业。** `PbVirtualTickPlan` 保留物理路径的预算分段合同；它本身不拥有配方、输入或付款收据。D15b 必须固定作业的成员／lane、配方与能力版本、并行批次、周期、单位 FE、已付费余数和预留输入；周期中途不能因补料、供电恢复、移机或升级而用旧余数完成更多操作。拆机先排空或转入唯一可恢复托管记录，不能免费重开。
- **实际接受量与通知分离。** ECO `ECOCraftingDispatchAccounting.apply/applyExact` 先把已接受作业量、结果与余料记入账本，再通知观察者；DataEnergistics `routeExact/consumeCurrent` 只减少已接受数量，余量仍归原记录。借鉴这两条边界，网络内部仍须由自己的 checkpoint 原子提交，外部异常的未知接受量不能当作零重试。

物理缓存仍在配方重载时失效，采样前过滤蜡／蜂蜜；精华、粗矿等升级转换继续留在物理适配器。D15a 没有因此声明这些升级已完成网络适配，也没有把物理 pending 的宽容 NBT 读取用作网络恢复器。新增内核无全局可变状态，数量接收器按物理 completer 生命周期复用，未增加逐操作扫描或无界缓存。

### 10.35 D16b2c2 核心维护费的事务边界（2026-09-21）
