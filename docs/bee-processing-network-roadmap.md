### 11.1 P0：先证明基础选择

**D01 — 固定行为与参考证据。** 前置：本设计。检查 `BeeSlotTickProcessor`、`BeeProduceProcessor`、`PbRecipeProcessor/Completer/Flusher`、全部工厂入口、AE2 及 Mekanism 父类调用链；列出要保留的基因、喂食、升级、并行和能耗口径。在现有测试包补充缺失的外部行为测试，记录一个普通与一个 IO 密集游戏世界基线。产物是可重跑用例、基线数据和本设计内的核对结果；通过条件为所有独立路径的实际计费、产量及 pending 状态都能被解释，不凭注释推断。

**D02 — 存储和 API 原型。** 前置：D01。用隔离的测试／基准源集比较 `long+BigInteger`、索引数组加稀疏大数、必要时可变分肢方案，执行第 10 节的操作分布；制作不接生产世界的 MEStorage 双向挂载与 SavedData 读写原型。验证超 long 展示、原生 AE2 聚合、缺失文件、保存时长和内存。通过条件为真实语义一致且有测量记录；若差异不足，选更容易审计的实现，原型不混入发布资源。

### 11.2 P1：领域模型与纯逻辑

**D03 — 能力快照与总能力数学（已实现，边界见 [10.6](bee-processing-network-evidence-foundation.md#s10-6)）。** 前置：D01。新增 `MemberCapabilitySnapshot`、`CapacityPoolIndex`、`VirtualLaneState`；从实际机器与升级服务读取 p／q／t／能耗及蜂位，`FactoryTierConfigSnapshot/Service` 的缓冲容量单列。测试异构机器、部分在线、升级变化、1.7 份／tick 示例、整数余数和完全不同的配方能力。通过条件为各配方条件上限等于成员贡献、同一进程不因可处理多个配方而复制，绝不叠乘不同机器的升级；此步不接管机器。

**D04 — ProductKey 和任意精度数量（已实现，见 [10.7](bee-processing-network-evidence-foundation.md#s10-7)）。** 前置：D02。以稀疏 long＋BigInteger 后端实现不可变组件键、数量升降级、零键回收；预约需要稳定身份时另加 entryId／generation，不提前固定分段数组后端。普通计数路径不创建 BigInteger。以 BigInteger 参考模型跑随机增减序列，覆盖 0、Long.MAX_VALUE、126 位以上、哈希碰撞、同 ID 不同组件及槽复用。通过条件为所有正负边界有明确行为，不存在截断，存储实现不含类型／总字节容量条件。

**D05 — 合法产物策略（已实现，见 [10.8](bee-processing-network-evidence-foundation.md#s10-8)）。** 前置：D04。新增 `ProductPolicyRegistry` 与 PB／动态蜂种适配接口，复用 `CentrifugeRecipeIndex` 解析合法链；重载构建不可变策略快照，正负缓存绑定 policyRevision。测试合法外部金锭、普通非产物、错误蜂种组件、容器嵌套、改名变体、动态发现与重载删除。通过条件为每个入口得到一致判断，产物目录不会递归扩张为全物品目录。

**D06 — 事务账本和转移暂存（已实现，见 [10.9](bee-processing-network-evidence-foundation.md#s10-9)）。** 前置：D04–D05。实现 `ProductLedger`、`ReservationBook`、`LedgerTransaction` 和有限 `TransferStaging`；校验生产提交、外部存取及内部消费的实际数量。使用模型式随机测试覆盖重复 commit、部分接受、预约取消、回调重入和模拟不变性。通过条件为余额／预约／暂存守恒，SIMULATE 不分配持久身份、不修改数量、dirty 或统计。

**D07 — 三作用域与分层组保留（已实现，见 [10.10](bee-processing-network-evidence-foundation.md#s10-10)）。** 前置：D06。实现 `ReservePolicy`、`GroupAllowanceAllocator`，支持 EXACT／BEE_TYPE／BASE_ITEM、ALL 和全局／规则两层；把“策略保留”与“事务预约”做成不同类型。测试第 6.4 节两个数值例子、跨层组交集、EXACT 例外和重复查询。通过条件为组总额度不被多个变体重复使用，规则 0 不放松全局保护；旧独立机策略测试保持通过。

**D08 — 规则编译、优先级和滞回（已实现，见 [10.11](bee-processing-network-evidence-foundation.md#s10-11)）。** 前置：D03、D07。实现 `ProcessingRuleIndex`、按配方能力匹配的候选队列、带权轮转与低／高水位状态机；支持输入键、标签、bee_type 和目标产物到合法配方的索引。测试规则重叠、无适用能力、被保留堵塞、高优先级缺料、严格优先选择和反复水位变化。通过条件为一次输入只有一个预约拥有者，默认公平模式低优先级可推进。

### 11.3 P2：先解决安全接管再生产（已验收，见 10.21）

**D09 — 持久化状态域。** 前置：D03–D08。新增 `NetworkDirectory`、`NetworkSavedData`、记录 codecs，保存所有账户、蜜蜂、喂食槽、升级、能力来源、在制计划和规则版本；索引从权威记录重建。拆成 D09a 完整权威 checkpoint／严格读取／显式创建／保存完成回执（查询 Snapshot 不含活跃事务明细，不能直接作为存档），D09b 预算化编码、不可变快照页与统一 checkpoint，后者的可行性验证从原 D28 前移，不能把 D02 百万键整表保存的秒级主线程暂停带入大规模闭环。测试 round-trip、未知版本、截断数据、缺键占位符、域丢失、重复身份、写失败重试和保存期间再次变更。通过条件为无法解码时隔离并保留原始数据，正常保存加载摘要一致，新 revision 不被旧保存回执清除，不默默生成空网络；分页后的账户与在制作业仍共享一次一致快照。

**D27 — 重载、配置与界面完整性。** 前置：D19–D26。接入配方／标签／KubeJS 重载屏障及能力配置 revision；所有新增配置登记到 NeoForge 配置系统、`ServerConfigScreen` 与 `zh_cn/en_us`，显示支持范围及故障原因。测试运行中删配方、改升级上限、关闭新建开关和缺少可选模组。通过条件为旧已付费计划可结算、非法新输入停止、现存网络始终有读取／恢复路径。

### 11.8 P7：后端定稿、故障验证与候选发布

**D28 — 根据实测优化存储／保存。** 前置：D02、D09、D20、D27。模型校验工具可提前独立交付（[10.63](bee-processing-network-evidence-current.md#s10-63)），不解除上述前置或授权更换生产后端。重跑候选基准与真实网络，只有热点证据支持时才切换索引数组、大数中间层、快照分页或 WAL；完整网络 checkpoint 协议先于分文件优化。验证任意精度、不断增长的合法类型、冷启动、保存时长、断写和回退。通过条件为优化没有引入配额或降低实际产量，持久化升级可检测并拒绝不兼容格式。

**D29 — 故障与长稳测试。** 前置：D28。做随机生产／提取／保留修改／拆连序列及长期运行，覆盖每个交接阶段、磁盘写失败、保存中断、重复 ID、旧快照、重启、多玩家和恶意包。核对物品／流体／蜜蜂／食物／升级／能量独立守恒与 pending 状态。通过条件为正常保存绝不复制或吞数据，无法确认的状态隔离且有恢复信息，不假装跨模组强制断电原子性。

**D30 — 游戏性能及兼容闸门。** 前置：D29。执行第 10 节 A/B/C/D、1×／64×／256×、大量类型和多人终端场景；SparkMCP 载入基线与对照，检查摘要、健康、来源、self time 与调用树，记录 profileId。客户端／专服分别测试依赖矩阵。通过条件为相同产出与能耗下证明收益，不以微基准或构建成功代替 MSPT 证据。

**D31 — 发布候选准备。** 前置：D30。定稿核心和端口配方、语言、模型、预览标识、可观察故障信息、只读恢复模式及现有发布说明；完成 `test`、`build`、`verifyReleaseArtifact` 和发布包核验，确认不打包参考源码／基准数据。通过条件为功能、兼容和恢复范围清楚；这一步准备候选，不自动推送、合并或发布外部平台。

**后续可选 D32 — AE2 请求型合成补货。** 前置：D22、D27、D31，另行估算。按照第 6.6 节验证原生 API 与 Thunderbolt 可选扩展，实现不可变规划快照、任务去重、crafting link 恢复和策略范围提示。它不阻塞基础目标库存维护，也不能以“提交前检查通过”宣称保护了所有外部 ME 库存。跨网合并、多桥、跨维度、区块加载与自动育种同样另行立项；用户已要求的同维度无线终端属于 D18f，不再列作可选。

### 11.9 每一步的交付与回退规则

采用**按行为闭环的小步开发、契约驱动验证和阶段关门验收**。路线图表示依赖，不代表已经验收；第 1.2 节是不变量来源，第 11 节定义交付物，第 10 节记录实测证据，第 13 节记录参考及取舍。变更这四者中任一项时检查其余三者，避免代码与设计各自推进。单步只承担一个主要风险；如果一个步骤同时包含调度、计费、恢复和 UI，应先拆成各自可验证的小步，再做联合阶段退出。

| 检验门 | 每步需要回答的问题 | 可接受证据与关门条件 |
| --- | --- | --- |
| G0 进入 | 前置是否完成？本步改变哪些行为、权威状态与不变量？ | 核对 worktree、前置提交、现有脏修改及真实依赖版本；实施前写清支持范围、失败路径、性能规模变量和不做的范围 |
| G1 契约 | 正常、拒绝、重放、模拟及恢复是否守恒？ | 可观察行为测试；计费／账本使用独立参考计算，候选绑定身份与 revision。涉及持久化则两种 decoder 与实际文件边界同时覆盖 |
| G2 接入 | 正式入口是否真的调用新服务？旧独立机是否保持行为？ | 有版本与依赖组合的真实专服探针；UI 改动另测客户端；测试从正式 ticker／菜单／能力入口进入，不用直接调用内核冒充端到端 |
| G3 性能 | 是否新增整表遍历、隐式复制、无限缓存或预算叠加？ | 固定规模／种子及预算计数测试，热路径与冷启动分别记录。单步最大耗时、积压及服务公平性可观察；有软预算不等于有严格耗时上限 |
| G4 交付 | 本步能否独立评审、复验和安全回退？ | 自审修复 → 按 [11.10](#s11-10) 运行受影响测试 → 必要 build／产物与运行检查 → 更新现有设计／changelog → 独立提交并推送 → 核对远端提交。任一必需检查失败则保持本步未验收 |

**阶段退出是联合验收。** D16b 需要蜂箱单独、离心单独、串联、缺电／补电、暂停、拓扑变化、真实跨 JVM 自动恢复、总预算和维护费同时成立；D16c 再增加玩家补料／有限取回／装笼后才退出 P3。后续 P4–P7 各自按本节同一检验门执行第 11 节已有矩阵。测试通过只能覆盖明确场景，不能承诺绝无性能或设计问题。

**性能证据分层。** 每步用可重复的操作数上限、缓存生命周期和功能守恒拦截结构性退化；修改 tick／加载热点时补相同夹具的实际耗时证据，记录源码提交、硬件、JVM、数据规模和冷／热状态。Spark／MSPT 的吞吐收益仍须第 [10.3](bee-processing-network-design.md#s10-3) 节同产出同能耗 A/B；D30 是完整压力和兼容验收，不是允许前面步骤忽视性能的理由。单条不可抢占操作超预算时单列为剩余风险，测量后决定拆分，不通过降低实际产量掩盖回归。没有完成的矩阵明确为待验收。

**把“完成”做成可追溯的判断。** 每步的证据段固定回答四项：设计契约／不变量、正式入口及状态变化、自动化用例／真实运行报告、剩余风险及所属后续门。性能同时列出规模变量（配方、输出、组件字节、成员、查看者）、每步工作单位和不可抢占调用；共享缓存必须说明键、失效、容量／保留根和停服清理。回归采用独立参考结果、固定种子或旧实现对照，不只检查新类是否被调用。状态按“实现中→本步验收→父步骤联合验收”推进，禁止把子步骤勾选累计成父阶段自动通过；文档的当前状态、路线和最终建议须同步更新，历史测量保留当时口径。

文档／资源等低影响改动不为凑数量添加镜像测试；代码按[11.10](#s11-10)运行受影响测试，全量回归集中到阶段收尾或公共底层风险。纯新增服务失败可以撤销本步；旧路径调用的抽象改动须一起回退适配器并跑独立机回归。已有测试世界数据时，只能使用兼容读取／恢复模式或恢复一致备份，不能删字段后运行不认识该存档的旧 JAR。指标进入现有日志或隔离探针；证据放 build 下，设计仅保存摘要与定位，不新建操作指南。

P1、P2、D13–D15、D16a／b1／b2a／b2b 已完成各自范围；D16b2c1／c2／c3a／c3b 的边界分别见 [10.34](bee-processing-network-evidence-production.md#s10-34)–[10.37](bee-processing-network-evidence-production.md#s10-37)，D16b 基础功能联合门见 [10.38](bee-processing-network-evidence-production.md#s10-38)，D16c 与 P3 联合验收见 [10.69](bee-processing-network-evidence-current.md#s10-69)。子步完成不会自动解除父步骤或阶段的门槛。

### 11.10 执行效率与逐步参考清单

每轮只认领一个可运行功能包：先核对状态、直接前置和实际 diff，列出最多一份缺口清单，再完成服务／界面／拒绝路径→聚焦行为测试→必要真实入口→自审修复→同轮登记合同／状态／证据→独立提交推送。已通过检查记录命令、源码／依赖哈希和范围，后续仅因相关变化或失败失效；不为每个控件或文档修改重新启动构建／游戏。验证按改动风险选范围，不按累计测试数或历史矩阵大小分派工作；已有证据可复用时不重新启动相同场景。参考代码只读，记录本地版本、具体类及不适用的约束；无适用新参考时复核既有契约，不为每步增加抽象或重复参考报告。

**产物保留：** Gradle 管理的 classes／generated／resources／moddev／tmp 与最新测试结果留原位；已签收报告、XML、源码／依赖哈希和截图汇总到 `build/network-gates/<步骤>`。历史运行实例与零散证据按日期归档到 `build/maintenance-<日期>`，保留原路径→内容哈希清单、恢复入口和成功／失败记录，全部核验后才清理原件。先排除运行进程与重解析点；未知文件先保留。因原始证据也在 build，日常迭代不执行全目录 `clean`；确需 clean 时先迁出完整证据并核验。归档不改变历史证据范围或把旧成功当作新版本验证。

**验证分层（2026-10-02）：**

- **实现迭代：** 运行受影响的行为测试；已有用例覆盖的重构、文案、布局微调不为凑数量新增测试。源码字符串／方法名断言只保留必要的注册与隔离约束，不能代替行为结果。资产守恒、权限、重放、保存恢复及生命周期仍是相关改动的必验项。
- **小步提交：** 默认只运行直接受影响的测试和一次必要编译／构建；全量快速回归集中到阶段收尾或公共基础代码变更。仅文档改动检查编码、链接和事实。只有新增真实入口或既有证据无法覆盖的行为变化才启动游戏；同一纵向功能完成后合并验证，不按每个 UI 子细节重新开服。已有 `network-stage-gate.ps1 -Scope Step` 仍可用于需要专服＋客户端的小步，但不再是每次提交的默认前置。构建／测试／游戏入口分别复用已通过结果，修复探针只重跑受影响入口。
- **阶段联合验收：** `-Scope Joint` 保留累计双依赖、跨 JVM 及相关玩家场景；涉及存档格式、依赖隔离、公共生产／收费／交接底层的改动需提前补受影响矩阵。小步通过不能关闭联合门，不能把尚未满足的游戏验收降为源码搜索测试。没有新改动、失败或未解风险时不反复运行同一矩阵。
- **测试维护：** 删除任意“检查数至少 20／40／80”门槛，保留行为结果、支持类型、协议字节预算及明确场景。默认复用现有夹具；新增测试只覆盖此前未覆盖的可观察回归，不为每个方法、控件、子步另建专用探针。探针自身出错先修夹具，不追加产品断言来凑通过数。退役功能的测试随调用链与旧实现一起整理；源码接线测试在触及相应模块时合并或替换为少量行为测试。读取文件的测试中也有资源、存档及编码校验，不能整类删除。

逐步源码清单统一维护在 **[13.3](bee-processing-network-references.md#s13-3)**，版本／目录统一在 **[13.2](bee-processing-network-references.md#s13-2)**，本节不再复制一份易漂移的步骤表。只复核本步实际触及的成功路径、失败／恢复、失效和线程约束；固定版本的既有读取结果可复用，API 或行为变化时再打开对应源码。在本步证据中写明新采用的原则和不能沿用的前提。只看到 save、snapshot 或 async 名称不算验证其复杂度与一致性。新增抽象必须对应当前可测的职责，后续步骤仍需重新读取实际接入点。

共享主分支 hotfix 到达时，先完成或妥善保存当前步骤，再 merge，重跑受影响回归。特殊蜜蜂／配方缓存修复会成为 D05、D13、D25、D27 的输入；D01 旧性能基线保留原提交标识，D30 重测当前独立模式基线。已完成与待做状态在本文更新，不为每步新增 Markdown 文件。

### 11.11 用证据驱动阶段推进

采用风险优先的纵向切片：每个子步在一个真实入口形成可运行闭环，先写拒绝／恢复条件，再实施最小服务；状态变化、成本模型和验收共同评审。行为决定写回主合同，阶段决定写本路线，验证结果写当前验收记录，不另建一套与实现脱节的架构文档。实现前比较“当前事实、目标契约、差异”，实现后按相同契约复核，避免仅按类名和功能清单判定完成。

### 11.13 按需启用的多模型协作与离线审核队列

本节只在用户明确要求多模型／多代理协作时启用；当前单代理开发按[11.10](#s11-10)自审、验证与交付，不等待不存在的审核队列。DSH 模型显示名不代表固定能力；启用时记录实际模型及工具限制，以同任务首次通过率、返工和审核成本决定分工。下述 Astra 表示用户指定的架构审查角色，模型互审不能替代测试。

**每日节奏与并发上限。** 建议 Astra 每日用约 10 分钟处理上一批证据、10 分钟冻结下一批合同、余下时间集中处理最难实现或最多两项高风险 diff；时间更少时优先审查关键路径并补充待办。离线前准备 1–2 天的独立任务，每张任务卡只包含一个可验收行为。起步采用两名实施者和一名独立验证者，每名实施者同时只认领一张卡；待审队列达到两项高风险变更后停止增加依赖它们的工作，转做已经批准的独立任务。根据实测首次通过率和 Astra 审查队列再增加并发，不按模型数量估算线性加速。

| 风险与适合任务 | 实施与复核 | Astra 离线时的完成边界 |
| --- | --- | --- |
| L：已冻结的文案、既定视觉规格下的静态资源、独立参考调查 | 一名实施者；另一模型核对 diff、链接／资源及支持范围 | 检查后提交、推送任务分支，进入待整合；未配置强制合入门前不自动进入网络分支 |
| M：接口固定的纯函数、测试夹具、既定协议的客户端展示 | 一名实施者；独立验证者从合同推导预期值，覆盖失败与生命周期 | 可构建、修复和提交；不得改变协议、验收断言或上限来通过测试；等待审核结论和整合验证 |
| H：账本／物品／FE 所有权、随机恢复、NBT／schema、线程、权限、可选依赖隔离、tick 调度、跨模块接口与性能结论 | Astra 先定合同，承担高难部分并最终审查；其他模型只实现明确授权的子块 | 完成自动检查与独立复核后停在待 Astra 审核；不能因为 Astra 离线、其他模型赞成或构建成功而合入 |

**任务卡最小内容。** 所有派工以本路线的任务 ID 为准，在 DSH 任务描述中携带以下字段，不另增仓库 Markdown：基线提交 SHA／前置任务及接口版本；允许修改的文件或目录与唯一负责人；目标行为／不变量／明确排除项；必须读取的合同锚点及本地参考版本和成功、失败、失效、线程入口；独立验收案例与固定种子／预算；所需测试、构建和游戏矩阵；预期交付及风险等级。前置代码未合入时只能进行不依赖实现的测试设计或参考调查，不允许自行猜接口。文件冲突、合同矛盾、API 缺失、损坏存档和未知外部结果须保留证据并回到待设计；两次同根因修复失败后交给更强模型诊断。

**工作区与提交。** 每个实施任务使用独立 Git worktree 和 `codex/<任务ID>-<职责>` 分支，从已经验收的网络提交创建；禁止多人同时写同一 worktree。任务分支有自己的 build、libs、run、世界和端口，不共享可写测试世界。同一步按“实现 → 自审修复 → 必需检查 → 提交 → 推送 → 核对远端 SHA”交付；推送仅保存待审成果，网络分支由单一整合者更新。正式源文件、同一测试文件和同一资源文件也只能有一名写者。主合同、路线、验收、参考、公共注册／协议及构建门由整合者统一维护；实施者通过任务回执提出精确修改建议，避免多张卡同时改总文档。

**审核回执与失效。** 实施者提交任务 ID、基线与 HEAD SHA、改动文件、行为摘要、命令／退出码、原始证据路径及 SHA-256、已知缺口；原始日志和截图留在忽略的 build 目录，可作为私有 CI 产物供跨机器复验，避免上传世界或身份敏感数据。独立验证者先读冻结合同、再读 diff，自行推导期望结果，给出“阻塞发现／已修复并重验／未覆盖”及复验命令。禁止删除失败用例、放宽断言、跳过测试或修改验收脚本来伪造通过。基线、HEAD、接口、依赖、配置或必需探针变化后，旧审核结论和受影响证据失效；整合者评估重跑范围，不能用旧绿灯批准新代码。

**合入门。** 依次通过任务合同、范围／编码、按 [11.10](#s11-10) 选择的行为回归、必要 build／JAR 核验、受影响的服务端／客户端／恢复矩阵、独立复核及所需 Astra 审核，再在最新已验收基线验证组合结果。合并冲突涉及语义时重新审查，不自动选某一边。文档 L 类无需游戏矩阵；纯函数 M 类无需为凑范围重跑整套客户端；H 类按 [11.9](#s11-9) 的实际入口补齐证据。父阶段、M04 和发布门仍由原合同裁决。

**可执行约束的现状。** 当前 `.github/workflows/build.yml` 对 PR 执行 build，push 只覆盖维护分支；它没有覆盖本地网络运行矩阵，也没有证明已配置远端分支保护、强制独立审批或令牌隔离。提示词与本地钩子都可被同权限进程绕过，因此本方案现阶段是流程约束，不能声称已经技术上禁止误合入。启用无人值守整合前，另行配置受保护网络分支、必需状态检查、审批失效规则和只由整合者持有的写入凭据，并实际验证一次拒绝直推与坏测试拒合；同一高权限 DSH 工作目录中换模型不能形成权限隔离。本轮继续沿用用户已授权的当前任务逐步检查、提交和推送，不把此建议扩展为修改账户或远端权限。

任务候选直接引用当前状态表和[11.5](#s11-5)–[11.8](#s11-8)，不复制已经验收的 D17 清单。启用协作时才补文件负责人、隔离 worktree 和精简任务回执；当前没有新建外部任务或启动其它模型。

DSH 实施提示可直接使用：“只执行任务卡的任务 ID；先核对基线、前置、合同和文件所有者。保留其他人的修改。不得扩大准入、改验收标准或修无关问题。完成失败路径测试和本卡必需检查后提交、推送你的任务分支，回报 HEAD、证据和未完成项。遇到合同冲突或未知资产结果，保留现场并提交待设计问题。” 独立验证提示可使用：“从任务卡独立推导预期行为，检查完整调用链及失败／恢复／失效，不依据作者总结认定通过；每个阻塞项给出触发条件、位置和可复验用例。只对当前 HEAD 给出结论，不擅自合入。” Astra 每次上线先消费这些紧凑回执，再按需打开原始证据，避免重读全部聊天历史。
